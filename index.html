What is Railspike

Introducing Railspike

Introducing Railspike and the plan-prompt

Gulko’s original

Railspike is a prompting framework we created to help my agentic developers and me stay on track in our work.

The pain points Railspike addresses are:

  • requirements drift,
  • misunderstandings in what’s being developed,
  • unprompted additions of undesired frameworks and third-party components, and
  • agent working for a long time before we realize what’s happening.

The goals of Railspike are to document much of the planning, keep intent clear as a feature is developed, and keep reminding the agent what it is working on.

This also makes it much easier to read and modify large amounts of agentic output in our preferred editors and viewers, which is often not the same as our console.

Railspike accomplishes this with multiple instruction prompts that split the development process into four steps: brainstorming, outlining, planning, and actual development work. This process has proven to work well for us in developing new features, reshaping existing features, fixing bugs, writing documentation, writing checklists for bigger pieces of work that take multiple cycles, and basically any task that we have thrown at it.

Sometimes even a simple, seemingly one-shot bugfix can go off-track when an agent misunderstands what we meant or intended, or chooses a solution that we do not agree with. Railspike has almost completely eliminated this occurrence by locking in what is planned. (Sometimes a one-shot fix really is, and we’ve had good results asking the agent this question.)

The main building block of Railspike is the plan-prompt: a plan, stored in a file, that the agent then follows as its prompt. Railspike began to take shape when we realized that, for most tasks, it is helpful to have the agent write its own prompt before actually starting the work. We could inspect this plan-prompt and alter it, also with the agent’s help, before any actual code was written.

We then set out to emulate a minimal planning process, not unlike agile or waterfall, where we first ideated on possible solution types and made a decision for what to do, fleshed out our decision in a detailed high-level plan, wrote an even more detailed development plan, breaking down the task into multiple atomic sub-tasks, and then began development following this third plan-prompt.

The process started out as one file with instructions, but we soon noticed that the instructions would often be forgotten out of the context window, so we split it into several files that we inserted into the conversation as they were needed. We then further added instructions for before, during, and after certain steps.

We spent a year refining these prompts as we used them to build multiple projects (mostly web-based online social spaces frameworks, but also some random things like documentation.)

We started keeping the prompting system in a repo so that it could be synchronized between projects.

As we worked on Railspike and refined it with several different coding agents like Cursor, Windsurf, Copilot, Claude Code, and Codex, we noticed that it can gradually bring different agents to work within similar constraints, often allowing us to compensate for weaker but less compute-intensive (and more affordable) models.

Many agents now include a built-in plan mode, where the agent explores the codebase and proposes a plan for you to approve before doing the actual edits. Railspike offers clear advantages over these. First and foremost, the plans are written as plaintext, searchable files in your repo, so they survive context window slide, compaction, your session, and transitions between multiple coding agents.

The second advantage is documentation: you (and your agent, even if you are now using a different one) can inspect the thinking that went into a feature.

Third, the process is consistent across agents, allowing a much more agent-agnostic development workflow. For example, we sometimes pass a task between Claude Code and Codex mid-task, because Codex appears to be better at complex features, while Claude Code seems to be better at UI.

This is not all, we keep finding new benefits, such as that we have to do a lot less manual explaining. We let the agent come up with its own explanation, and correct it if needed. Most of the time it has the right idea.

Eventually, we started recommending this process to others and seeing it help them, and realized that it needed a catchier name than FEATURE_DEVELOPMENT_PROCESS.md. We also realized that it needed a debug mode, so we added that.

And here it is!

Railspike is super easy to drop into an existing project. If you want to start now, super quickly, just copy it anywhere into your project and next time you’re developing a feature, just append to your prompt: “Write Step 1 of RAILSPIKE.md.” Important note: Your original prompt will be preserved in the generated Step 1 document, so don’t write anything you don’t want to end up in your repo.

Railspike is pretty stable at this point, but if you want to keep up with the hopefully infrequent updates, you can also use it as a git submodule. Instructions for this are included.

Every once in a while, a tool comes along that changes the way you work. Today, we’re introducing one.

It’s called Railspike.

Here’s the problem. You give an AI agent a task. It’s brilliant. It’s fast. And twenty minutes later, you look up and it’s building something you never asked for. It drifted from the requirements. It misunderstood what you meant. It pulled in three frameworks you didn’t want. And it’s been running the whole time, and you had no idea.

We’ve all been there. It’s not a small problem. It’s the problem.

So we asked a simple question: what if the agent knew exactly what it was building, and never forgot?

That’s Railspike.

At its heart is one simple idea. We call it the plan-prompt. Before the agent writes a single line of code, it writes its own prompt: a plan, in a file, that it then follows. You read it. You change it. The agent helps you change it. And only then does the work begin.

It sounds simple. It is simple. That’s what makes it so powerful.

Railspike takes you through four steps: brainstorm, outline, plan, build. First you explore the options and make a decision. Then you shape that decision into a high-level plan. Then you break it down into small, atomic tasks. And then, and only then, the agent builds. Every step is written down. Every step is something you can see.

New features. Reworking old ones. Bug fixes. Documentation. Checklists for big projects that take many cycles. We’ve thrown everything at it. It just works.

Even the tiny one-line bug fix, the one you were sure the agent couldn’t get wrong, can go sideways. Railspike has almost completely eliminated that. Because once the plan is locked in, it’s locked in.

October 2026

If you’ve worked with AI coding agents for any length of time, you’ve probably had this experience. You ask the agent to do something reasonable. It starts working. Twenty minutes later you look over and find it has built something you didn’t ask for, using a framework you didn’t want, on the basis of a misunderstanding you could have cleared up in one sentence if you’d known it existed.

The usual reaction is to blame the agent. But I don’t think the agent is the real problem. The real problem is that the plan exists only in the agent’s head, and the agent’s head is a context window that is constantly losing things.

Railspike is what we built to fix that. It’s a set of prompts that makes the agent write its plan down before it does anything else. That turns out to matter more than you’d expect.

The idea started with a small observation: for most tasks, it helps to have the agent write its own prompt before starting work. Not the code, the prompt. Then you can read it, and change it, before a single line of code exists. We call this a plan-prompt: a plan, stored in a file, that the agent then follows as its instructions.

Why does this work so well? I think it’s because it moves the misunderstanding to the cheapest possible place. Every misunderstanding has to surface eventually. The question is whether it surfaces in a paragraph of English you can fix in ten seconds, or in two thousand lines of code you have to read, understand, and throw away. Writing the plan first is how you make it the former.[1]

From there we did the obvious thing, which was to borrow from how people already plan software. Railspike splits work into four steps. First you brainstorm: what are the possible kinds of solution, and which one do we want? Then you outline the chosen approach as a high-level plan. Then you write a detailed development plan that breaks the work into small atomic tasks. Then the agent builds, following that third plan-prompt.

This sounds like a lot of ceremony for fixing a bug. It isn’t, in practice, and in any case the bugs are where it surprised us most. A fix that looks like a one-shot job is exactly where you don’t bother to check the agent’s understanding, which makes it exactly where the agent goes wrong. Since we started using Railspike, that has almost stopped happening.

That said, some one-shot fixes really are one-shot fixes, and running them through four stages would be a waste. What works for us is simply to ask the agent which kind of task this is: something it can just do, or something that should go through Railspike. Its answers have been good. Deciding whether a task needs a plan is a much easier question than doing the task, which may be why agents handle it well.

We didn’t get here directly. Railspike began as a single file of instructions. The trouble was that agents would forget the instructions as they scrolled out of the context window. So we split the file into several, and fed each one into the conversation when it was needed. Then we added instructions for before, during, and after particular steps. We spent about a year refining this while building real projects, mostly frameworks for online social spaces, plus some odd things like documentation. At some point we put it in its own repo so we could keep it in sync across projects.

Something we didn’t expect: Railspike made different agents behave more alike. We used it with Cursor, Windsurf, Copilot, Claude Code, and Codex, and over time they started working within the same constraints. One consequence was that weaker, cheaper models became usable for work we’d otherwise have given to more expensive ones. A lot of what makes a model seem smart, it turns out, is knowing what it’s supposed to be doing.

A reasonable question at this point is: don’t agents already have plan modes? Many do. The agent explores the codebase and proposes a plan for you to approve before it makes changes. That’s the same instinct, and it’s a good one. But Railspike differs in three ways that I think matter.

The first is that the plans are plain, searchable text files in your repo. So they survive things that plans otherwise don’t: the context window moving on, compaction, the end of your session, and switching from one agent to another.

The second is that they’re documentation. Months later, you, or your agent, even if you’ve switched to a different one, can look at the thinking that went into a feature. Code tells you what was built. It rarely tells you what was intended.

The third is that the process is the same across agents, so your workflow stops depending on any one of them. We sometimes hand a task from Claude Code to Codex in the middle, because Codex seems better at complex features and Claude Code seems better at UI. That only works because the plan doesn’t live inside either of them.

We keep finding other benefits we didn’t plan for. One is that we do much less explaining. Instead of describing the task in detail ourselves, we let the agent write its own explanation and just correct it where it’s wrong. Most of the time it has the right idea already. Correcting a description is a lot less work than writing one, which in retrospect is probably why this works so well.

There’s a machine railroads use called a tracklayer. It rides on the rails it has just laid, and lays the next section ahead of itself as it goes. That’s roughly what Railspike asks an agent to do: lay down the plan, then run on it.

Eventually we found ourselves recommending this to other people, and it helped them too, at which point it clearly needed a better name than FEATURE_DEVELOPMENT_PROCESS.md. We also realized it needed a debug mode, so we added one.

If you want to try it, it’s easy. Copy Railspike anywhere into your project, and the next time you’re working on a feature, append this to your prompt: “Write Step 1 of RAILSPIKE.md.” One warning: your original prompt is preserved in the Step 1 document it generates, so don’t write anything you wouldn’t want in your repo.

Railspike is fairly stable by now. If you want the occasional update, you can also use it as a git submodule; instructions are included.

Notes

[1] This is not a new idea. It’s more or less why people write specs. What’s new is that the agent will write the spec for you, which removes the main reason people skip it.

I want to tell you about a little trick we figured out, because it’s so simple you’d think everybody would already be doing it, and yet nobody was. Well, at least we weren’t.

Here’s the situation. You’ve got one of these AI agents, and it’s a very clever fellow. You tell it, “Fix this bug,” and it goes off and works. And it works and works, and you go get a sandwich, and you come back, and it has done something. Only it’s not what you wanted! It misunderstood you. Or it decided, all on its own, that what this project really needed was some big framework you’ve never heard of. And it’s been happily doing this for twenty minutes, and you didn’t know.

Now, you could get mad at the agent. But that doesn’t help, so let’s think about what’s really going on.

When you give the agent a task, it makes a plan. It has to. But where’s the plan? It’s in the agent’s head, so to speak. In its context window. And the trouble with the context window is that things fall out of it. It’s like trying to remember a phone number while somebody keeps telling you other numbers. After a while, the first one is gone. And you can’t see the plan either! So you’ve got a plan that the agent is forgetting and you can’t check. That’s two problems, and it’s no wonder things go wrong.

So the idea is: write the plan down. In a file. That’s it. That’s the whole trick.

Well, almost the whole trick. Here’s the part that’s a little bit nice. We noticed it helps to have the agent write its own prompt before it starts working. Not code, just a description, in plain words, of what it’s going to do. Then you read it. And you find out right away whether it understood you. If it didn’t, you fix a sentence. You don’t fix a thousand lines of code. You fix a sentence! We call this thing a plan-prompt, because it’s a plan, and then the agent uses it as its prompt and follows it.

You see, the agent will fool you. Not on purpose; it just misunderstands, the same as anybody. And the easiest one to fool is you, because you assume it understood. The plan-prompt is how you check. It’s like an experiment: before you believe the thing works, you look.

Then we got a little more organized about it. We split the work into four steps. First, brainstorm: what are the different ways we could solve this, and which one do we like? Second, outline: take that choice and write a high-level plan. Third, plan: break it into small pieces, little atomic tasks, so detailed you can’t get lost. And fourth, do the work, following that third plan-prompt step by step.

People say, “Isn’t that an awful lot of fuss for a small bug fix?” And I would have said so too. But it’s the small ones that get you! The little fix you were sure the agent understood, so you didn’t check. Since we started doing this, that kind of thing has almost completely stopped happening.

Now, I don’t want to oversell it. Sometimes a one-line fix really is a one-line fix, and making a big production of it would be silly. So what do you do? You ask the agent! “Is this something you can just do, or should we use Railspike?” And it turns out it’s pretty good at telling the difference. Which makes sense, when you think about it: knowing whether a job is easy is a lot easier than doing the job.

Now, it didn’t start out so neat. At first it was one file of instructions. And the funny thing is, the instructions had the same problem as the plans! The agent would forget them as they slid out of its memory. So we chopped them into several files and handed each one to the agent right when it needed it, the way you’d hand a surgeon the next tool. Then we added instructions for before, during, and after certain steps. We fiddled with it for about a year while building real things, mostly software for online social spaces, and some odd jobs like documentation. We kept the whole thing in a repo so we could share it between projects.

And then we found something we weren’t looking for, which is always the most fun. We were using it with all sorts of agents: Cursor, Windsurf, Copilot, Claude Code, Codex. And they started behaving alike! Different agents, same discipline. Even the cheaper, less powerful models started doing good work. It turns out a lot of what looks like intelligence is just knowing what you’re supposed to be doing.

Somebody’s going to ask, “Don’t the agents already have a plan mode?” Yes, many of them do now. The agent looks around the code and proposes a plan, and you approve it. That’s the right idea. But there are three things Railspike does that I think are important.

First, the plans are plain text files in your repo, and you can search them. So they don’t disappear when the context window moves on, or when the conversation gets compacted, or when your session ends, or when you switch to a different agent.

Second, they’re a record. Months later, you can go back and see what you were thinking when you built something. And so can your agent, even a different one. The code tells you what was built. It doesn’t tell you what you were trying to do.

Third, it works the same way with every agent. Sometimes we hand a job from Claude Code to Codex right in the middle, because Codex seems better at the complicated stuff and Claude Code seems better at the user interface. That only works because the plan isn’t stuck inside either one of them.

And we keep finding new things it’s good for. Here’s a nice one: we hardly have to explain anything anymore! We used to write out long descriptions of what we wanted. Now we let the agent explain it to us, and we just correct it where it’s wrong. And most of the time it has the right idea. It’s a lot easier to grade a student’s answer than to write the textbook.

There’s a machine the railroads use called a tracklayer. It rolls along on the track it just put down, and lays the next piece in front of itself. I like that. That’s what we’re asking the agent to do: lay down the plan, then ride on it.

Eventually we started telling other people about this, and it helped them too. And then we had to admit that FEATURE_DEVELOPMENT_PROCESS.md was not a very good name. So now it’s Railspike. We also added a debug mode, because we needed one.

It’s pretty stable now. But if you want the occasional update, you can also use it as a git submodule. The instructions are included.

Try it. See what happens. That’s the only way to find out anything.

A Plain Account of Railspike

In the style of George Stephenson · a pastiche written for fun, not a real quotation and not written or endorsed by them

Gentlemen,

I am a plain man. I was set to work at the pit when I was a lad, and I learned my letters late, so you must forgive me if I speak of your new engines in the only way I know, which is the way I would speak of a railway.

I am told you have engines now that think. I am told they work very fast and very hard, and that a man may set one going in the morning and find by dinner that it has carried his train somewhere he never meant it to go. It has laid a branch line nobody surveyed. It has brought in machinery nobody ordered. And it has run on and on in the wrong direction before anyone thought to look out of the window.

I know this trouble. It is the trouble of building without a survey.

When we made the line between Liverpool and Manchester, there was a great bog in the way called Chat Moss, and a good many clever men said no railway could ever cross it. We crossed it. But we did not cross it by throwing down iron and hoping. We crossed it by working out first how that soft ground could be made to bear the load, and then doing exactly that. A railway is not built by laying rails. It is built by deciding, before any rail is laid, where the line shall go, over what ground, at what gradient, and why. Once that is settled and written down, any honest crew can lay it. Until it is settled, the finest crew in England will only make a mess faster.

Railspike is a survey for your thinking engines.

The chief part of it is what its makers call the plan-prompt: a plan, written in a file, which the engine then follows as its orders. They found that for most work it answers well to have the engine write out its own orders first, before it touches anything. Then a man may read them, and mend them, with the engine’s help if he likes, before a single rail goes down. If the engine has misunderstood him, he learns it from a page of plain writing and puts it right in a minute, instead of tearing up a mile of track.

The work goes in four stages, as any line worth building does. First, the engine and the man consider the several routes that might be taken, and choose one. Second, the chosen route is drawn out as a general plan. Third, that plan is worked out in close detail and broken into small tasks, each so plain that no one can go wrong on it, the way a line is broken into lengths, each with its own cuttings and embankments. Fourth, the work is done, following that third plan and no other.

You may say this is a great deal of fuss to mend one broken sleeper. I would have said so myself. But it is the small jobs a man does not trouble to check, and so it is the small jobs that go wrong. The makers tell me that since they began working this way, such a thing has very nearly stopped happening.

I will not pretend that every job wants a survey. Sometimes a loose bolt is only a loose bolt, and a man should tighten it and get on. The makers have found that the best way to tell the one from the other is simply to ask the engine: is this a small job it may do directly, or a piece of work that wants the full survey? They tell me its answers have served them well.

And because the plans are written down, a man may read them at his own desk, in his own good light, instead of peering at the gauges while the engine is running.

It was not built in a day. At first it was a single sheet of instructions. But these engines have short memories. They keep only so much in mind at once, and what they were told at the start falls away as the journey goes on. So the instructions were cut into several sheets, each handed over at the station where it is wanted, like orders passed up to a driver along the line. Then further orders were added for before, during, and after certain stages. The makers spent a year at it, building real works: mostly meeting places for people online, and a few odd jobs besides, such as documentation. They kept it in a repository of its own, so every works might draw from the same plans.

And then they found something I was very glad to hear. They used it with engines of five different makes, Cursor, Windsurf, Copilot, Claude Code, and Codex, and found that under the same orders the different engines began to run alike. Even the smaller and cheaper engines did work that had wanted bigger ones. This is no surprise to me. A modest locomotive on a well-surveyed line, with easy gradients, will do better than a great one floundering over bad ground.

Some of the newer engines come with a planning mode of their own. The engine looks over the ground and proposes a plan for the man to approve before it does the work. That is a sound instinct, and I respect it. But Railspike goes further in three respects.

First, its plans are plain written files, kept in the works itself, where anyone may search them. So they are not lost when the engine’s memory runs short, nor when its notes are cut down, nor when the day’s work ends, nor when one engine hands the job to another.

Second, they are a record. Months afterward, a man, or his engine, even an engine of another make, may look back and see what was intended. The finished line tells you where the rails went. It does not tell you why.

Third, the method is the same whatever engine you use. The makers will sometimes take a job off Claude Code partway and give it to Codex, because Codex seems the better at heavy work and Claude Code at fine finishing. That can only be done because the plan belongs to neither engine. It belongs to the line.

And the makers keep finding fresh advantages. Not the least of them is that they must explain a good deal less. Rather than writing out every instruction themselves, they let the engine set down its own account of the work, and correct it where it is wrong. They tell me it has the right idea far more often than not. Any foreman knows it is quicker to check a man’s understanding than to give him his orders word by word.

In time the makers began recommending it to others, and found that it served them too, and so it wanted a better name than FEATURE_DEVELOPMENT_PROCESS.md. They also found it wanted a means of hunting down faults, and so they added a debug mode.

And here it is.

It is easily put to work. Copy it anywhere into your works, and the next time you begin a new feature, add these words to your orders: “Write Step 1 of RAILSPIKE.md.” A word of caution: your original orders will be kept in the Step 1 document it writes, so put nothing in them you would not want kept in your records.

It runs steadily now. But if you would have the occasional improvement as it comes, you may also take it in as a git submodule. The instructions are included.

There is a machine, I am told, that lays its own track ahead of itself, riding on the rails it has just put down. I should have liked to see it. Railspike asks your engine to do the same: lay down the plan, and then run upon it.

Survey first. Then lay the line.

[ANNOUNCE] Railspike

In the style of Linus Torvalds · a pastiche written for fun, not a real quotation and not written or endorsed by them

Hi all,

So this is Railspike. It’s not a framework in the “install forty packages and read a manifesto” sense. It’s a handful of Markdown files. You copy them into your tree. That’s the install.

Why does it exist? Because AI coding agents are very good at doing the wrong thing very fast. You give an agent a task, you go do something else, and when you come back it has decided your project needed a new framework, misunderstood what you actually asked for, and spent twenty minutes happily building on top of that misunderstanding.

That’s not really a bug in the agent. It’s a bug in the process. The plan only exists in the agent’s context window, and the context window is a leaky bucket. Stuff falls out. Including the stuff you cared about.

Quite frankly, the fix is embarrassingly obvious: write the plan down.

The core thing is what we call the plan-prompt. Before the agent touches any code, it writes its own prompt: a plan, in a file, that it then follows. You read it. You fix it. If the agent misunderstood you, you find out by reading two paragraphs of English, not by reviewing a 2,000-line diff that should never have existed in the first place. Reviewing intent is cheap. Reviewing code built on the wrong intent is expensive, and then you throw it away anyway.

If you think about it, it’s just a good commit message, written before the code instead of after.

The process has four steps:

  1. Brainstorm the possible approaches and pick one.
  2. Outline the chosen approach.
  3. Write a detailed plan that breaks the work into small, atomic tasks.
  4. Build, following that plan.

Yes, somebody will say that’s overkill for a one-line bug fix. That somebody has not watched an agent “fix” a one-line bug by rewriting the whole module. The trivial fixes are exactly where nobody bothers to check, so they’re exactly where things go wrong. Since we started doing this, that kind of thing has pretty much stopped happening.

That said, I’m not religious about it. Sometimes a one-line fix really is a one-line fix, and pushing it through four planning stages is just bureaucracy. So ask the agent first: is this a one-shot fix, or does it need Railspike? In practice it’s been good at telling the difference. Use the process when it pays for itself, and skip it when it doesn’t.

And because it’s all plain text in files, you read it in your own editor. Not in some console that scrolls away while you’re looking at it. If something is important enough to review, it’s important enough to review in a tool you actually like.

Some history. It started as one instruction file. That didn’t work, because the agent forgot the instructions the same way it forgot the plan: once they fell out of the context window, they were gone. So it got split into several files, each one fed in when it’s actually needed, plus instructions for before, during, and after certain steps. We spent about a year beating on it while building real projects, mostly frameworks for online social spaces, plus random things like documentation. It lives in its own repo so every project gets the same version. Obviously.

The part I didn’t expect: it makes different agents behave the same. We’ve run it with Cursor, Windsurf, Copilot, Claude Code, and Codex, and under the same process they all start working within the same constraints. Cheaper, weaker models suddenly do useful work. It turns out a lot of “model quality” is just the model knowing what it’s supposed to be doing. A mediocre tool with a good process beats a smart tool with no process.

“But my agent already has a plan mode.” Fine. Many do, and the idea is right: look at the code, propose a plan, get approval. Railspike is better in three ways, and none of them are subtle.

  1. The plans are plain, searchable text files in your repo. They survive the context window, compaction, the end of your session, and switching agents. A plan that lives inside some tool’s session is a plan you are going to lose.
  2. It’s documentation. Six months later you, or whatever agent you’re using by then, can see what was intended and why. Code tells you what. It doesn’t tell you why, and “why” is the part that’s actually hard to reconstruct.
  3. It’s the same everywhere. No agent lock-in. We regularly move a task from Claude Code to Codex halfway through, because Codex seems better at the complex stuff and Claude Code seems better at UI. That only works because the plan isn’t owned by either of them. It’s owned by the repo, which is where it belongs.

And it keeps paying off in ways we didn’t plan for. The big one: a lot less explaining. You don’t write the spec. You let the agent write its own explanation, and you fix what’s wrong. Most of the time it’s right. Reviewing is cheaper than writing, which is something every maintainer already knows.

At some point other people started using it, and it helped them too, so it needed a better name than FEATURE_DEVELOPMENT_PROCESS.md. It also grew a debug mode, because it needed one.

That’s not a bug, that’s the point. But it does mean that if your prompt includes a rant about your coworker, the rant gets committed too. Don’t do that.

It’s stable. If you want the occasional update, use it as a git submodule. Instructions are included.

Sketch of Railspike, with Notes

In the style of Ada Lovelace · a pastiche written for fun, not a real quotation and not written or endorsed by them

The engines of the present day are of a kind which Mr. Babbage himself could scarcely have imagined. They do not merely compute; they compose. A person may describe in ordinary language what they wish done, and the engine will set about doing it, writing out whole programmes of its own accord, with a speed no human clerk could approach.

Yet I find that the oldest difficulty remains exactly where it was. I wrote long ago that the Analytical Engine “can do whatever we know how to order it to perform.” These newer engines are far more capable, but the principle has not been repealed. An engine that has misunderstood its orders will carry out the misunderstanding with perfect diligence. It will wander from the requirements; it will introduce apparatus nobody wished for; and it will continue in this manner for a considerable time before anyone thinks to inquire.

The cause, I believe, lies in where the orders are kept. They reside only within the engine’s present attention, which its operators call the context window, and that attention is of limited extent. As the work proceeds, the earliest instructions are displaced by later matter, until the engine has quite lost sight of its original purpose.

The remedy proposed by the authors of Railspike is simple to the point of austerity: the orders must be written down, and kept.

Its principal element they call the plan-prompt: a plan, set down in a file, which the engine afterwards follows as its instructions. The engine is first asked to compose its own orders before undertaking any work. These may then be read and amended by the operator, with the engine’s assistance if desired, before a single line of the programme is written. A misunderstanding discovered in a paragraph of plain prose is corrected in a moment. The same misunderstanding discovered in a finished programme must be undone at very great cost.

I am reminded of the Jacquard loom, which weaves its patterns by following a chain of punched cards. No weaver would set the loom running and only then begin to consider the design. The pattern is decided first and fixed upon the cards; the loom is merely faithful to it. Railspike asks that the engine’s pattern be fixed in the same way.

The work proceeds in four stages. First, the several possible methods of solution are considered, and one is chosen. Second, the chosen method is set out as a general plan. Third, that plan is developed in close detail and divided into small and distinct operations, each simple enough to be executed without ambiguity, much as I once divided the computation of the Bernoulli numbers into a table of individual steps. Fourth, the work itself is performed, according to that third plan.

It may be objected that so much preparation is excessive for the correction of a trifling fault. Experience suggests otherwise. It is precisely the trifling corrections which are left unexamined, and so it is precisely these which go astray. Since the authors adopted this method, such errors have very nearly ceased. I should add, in fairness, that a trifling correction is sometimes exactly that; and the authors report good results from simply asking the engine whether a given task requires the full method or may be done directly.

There is a further convenience. Because the plans are written in files, they may be studied at leisure, in whatever manner of reading the operator prefers, rather than in the narrow and ever-scrolling window of the engine’s console.

The method did not arrive complete. It began as a single document of instructions; but the engine forgot those instructions in just the manner it forgot its plans. The document was therefore divided into several, each supplied to the engine at the moment it is wanted, and further instructions were added for before, during, and after particular stages. The authors spent a year refining it while building works of real substance, chiefly frameworks for online social gatherings, together with some miscellaneous productions such as documentation. They kept it in a repository of its own, so that every project might draw upon the same text.

They then observed a circumstance I find most interesting. The method was employed with engines of five different constructions: Cursor, Windsurf, Copilot, Claude Code, and Codex. Under the same instructions, these engines came to work within the same constraints, and even the lesser and less costly among them produced useful work. This accords entirely with my former view. The quality of an engine’s output depends in great measure on the clarity of the orders it is given.

It will be observed that many such engines now possess a planning mode of their own, in which the engine surveys the existing work and proposes a plan for the operator’s approval. The instinct is a sound one. Railspike nonetheless offers three advantages.

First, its plans are plain, searchable files kept within the project itself. They therefore survive the limits of the engine’s attention, the condensing of its record, the close of the working session, and the transfer of the work from one engine to another.

Second, they form a record. Months afterwards, the operator, or the operator’s engine, even one of a different construction, may consult the reasoning that went into a feature. The finished programme shows what was done. It cannot show what was intended.

Third, the method is the same whatever engine is employed. The authors will sometimes transfer a task from Claude Code to Codex in the midst of the work, Codex appearing the more capable in complex features and Claude Code in matters of the interface. This is possible only because the plan belongs to neither engine.

Nor are these the only benefits; the authors continue to discover others. Chief among them is that far less explanation is required of the operator. Rather than describing every particular, the operator permits the engine to compose its own account of the task, and corrects it where necessary. In most instances the engine’s understanding proves sound. To examine and amend a description is a considerably lighter labour than to compose one.

In time the authors recommended the method to others, who found it equally serviceable, and it was judged to deserve a better name than FEATURE_DEVELOPMENT_PROCESS.md. A debug mode was also added for the detection of errors, without which no system of operations can be considered complete.

To employ it, copy it anywhere into the project, and when next beginning a feature, append to the instructions: “Write Step 1 of RAILSPIKE.md.” The operator should be warned that the original instructions will be preserved in the Step 1 document so produced, and should therefore contain nothing they would not wish to see kept in the repository.

The method is now settled. Those who wish to receive its occasional improvements may instead include it as a git submodule; the necessary instructions are included.

The engine can do whatever we know how to order it to perform. Railspike is a means of knowing.

Make the robot write it down first

In the style of rachelbythebay · a pastiche written for fun, not a real quotation and not written or endorsed by them

Here’s a scenario. You have one of those coding agents. You ask it to fix something small: a button that renders in the wrong place, say. You go get a cup of tea. When you come back, the button is fixed, sort of, and also there’s a new dependency in the build, a helper library you’ve never heard of, and a refactor of two files that had nothing to do with the button. The agent is very pleased with itself.

If you’ve been doing this for any length of time, you know exactly how this feels. It’s the same feeling as finding out that someone “cleaned up” a config while they were in there for something else. Nobody asked them to. And now you get to figure out which of the forty changed lines actually mattered.

The agent isn’t being malicious. It’s doing what it thinks you wanted. The problem is that what it thinks you wanted lives in exactly one place: its context window. You can’t see it, and it doesn’t stay put. Things scroll off. Whatever you said at the start gets fainter and fainter until it’s basically gone, and then the agent is running on vibes.

So we started doing something boring about it. We made the agent write down what it was going to do, in a file, before doing any of it. We call this file a plan-prompt, because it’s a plan, and then the agent follows it as its prompt.

That’s it. That’s the trick. I realize it doesn’t sound like much.

But think about where you find out about a misunderstanding. If the agent writes “I will add a date-picker library to handle this,” you see that in a paragraph of text, you go “no, absolutely not,” and you fix the sentence. Ten seconds. If you don’t see it until the diff, you’re now reviewing code that was built on a bad assumption, and you’re going to throw all of it away anyway. Same misunderstanding, wildly different cost.

This grew into a whole process, which we eventually called Railspike. Four steps: brainstorm the possible approaches and pick one, outline the chosen one, write a detailed plan broken into small atomic tasks, and then actually build, following that plan.

Yes, I know. Four steps to fix a button. But the button fixes are exactly where this pays off, because those are the ones where nobody checks. “It’s a one-liner, what could go wrong?” Lots, it turns out. Since we started doing this, the agent wandering off on a “simple” fix has pretty much stopped happening.

To be fair, sometimes a one-liner really is a one-liner. For those, we just ask the agent whether it’s a one-shot fix or a Railspike job. It’s been pretty good about making that call.

Another nice side effect: all of this is plain text sitting in files. So you read it in your own editor, the one you’ve spent years getting comfortable with, instead of squinting at a terminal that keeps scrolling while you’re trying to read.

Of course, the first version didn’t work. It was one big instruction file, and the agent forgot the instructions for exactly the same reason it forgot the plans: they fell out of the context window. So the file got split up, and each piece gets fed in when it’s needed, plus some extra instructions for before, during, and after certain steps. Then came a year of grinding on it while building actual projects, mostly frameworks for online social spaces, plus some random stuff like documentation. It lives in its own repo so every project gets the same copy.

Here’s the part I didn’t see coming. We ran it with Cursor, Windsurf, Copilot, Claude Code, and Codex, and they started behaving like each other. Same constraints, same shape of output. Even the cheaper, weaker models started being useful. A surprising amount of what looks like “the model is smart” turns out to be “the model knows what it’s supposed to be doing.”

Now, someone is going to point out that agents have plan modes now. Many of them do: look around the code, propose a plan, wait for a thumbs-up. Good. Same instinct. Railspike still wins on three counts.

First, the plans are plain, searchable text files in your repo. They survive the context window, compaction, the end of the session, and switching agents. A plan that only exists inside some tool’s session is a plan with an expiration date.

Second, they’re a paper trail. Six months later, when someone asks “why on earth does it work this way?”, you (or your agent, even if it’s a different one by then) can go look. The code tells you what happened. It doesn’t tell you what anyone meant.

Third, it doesn’t care which agent you use. We sometimes hand a task from Claude Code to Codex in the middle, because Codex seems better at the complex stuff and Claude Code seems better at UI. That only works because the plan isn’t trapped inside either one.

And it keeps turning up new benefits. The one I like most: way less explaining. You don’t have to type out an essay about what you want. The agent writes up its own explanation, and you fix the parts it got wrong. Most of the time, it got it right. Editing beats authoring, every time.

Eventually other people started using it, and it helped them too, and it became clear that FEATURE_DEVELOPMENT_PROCESS.md was not going to cut it as a name. It also picked up a debug mode along the way, because of course it did.

If you want to try it: copy it anywhere into your project. Next time you start on a feature, tack this onto your prompt: “Write Step 1 of RAILSPIKE.md.” Heads up: your original prompt gets saved into that Step 1 document, so don’t put anything in there you wouldn’t want sitting in your repo forever.

It’s pretty stable now. If you want the occasional update, use it as a git submodule. Instructions are included.

So, yeah. Make the robot write it down first. You’ll thank yourself later.

Keeping Agents on Topic

In the style of Daniel Gackle · a pastiche written for fun, not a real quotation and not written or endorsed by them

I’ve been thinking about why AI coding agents go off the rails, and I think it’s for the same reason threads do.

A thread starts with a specific topic. Someone posts an article, the first few comments engage with it, and then somewhere around the fortieth reply people are arguing about something that has nothing to do with the original post. Nobody decided to do that. Each comment was a reasonable response to the one right above it. The drift happens one small step at a time, and by the time anyone notices, the original topic is gone.

Agents do something very similar. You ask for a specific fix. The agent starts working, and each step is a reasonable response to the step before it. But the original request lives only in its context window, and as the work goes on, the earliest material gets crowded out. Twenty minutes later it has misunderstood what you wanted, added a framework nobody asked for, and is still going, and you didn’t notice because each individual step looked fine.

The thing that helps with threads, as far as I can tell, isn’t heavier moderation. It’s having the intent written down somewhere everyone can point to. That’s most of what the site guidelines are for. They don’t depend on anyone remembering them. They’re just there, and when a thread drifts, you can link to them and people can see what the conversation was supposed to be.

Railspike applies the same idea to agents. Its main building block is what its authors call a plan-prompt: a plan, stored in a file, that the agent then follows as its prompt. Before writing any code, the agent writes down what it intends to do. You read it, and you can change it, with the agent’s help if you like. If there’s a misunderstanding, you find it in a paragraph of plain text rather than in a pile of code you’d have to unwind.

The process has four steps: brainstorm possible approaches and pick one, outline the chosen approach, write a detailed plan broken into small atomic tasks, and then build, following that third plan-prompt.

That may sound like a lot for a small bug fix. But in my experience the small things are where people don’t look closely, so they’re where things go sideways. The authors report that since they started using Railspike, simple fixes going off track has almost stopped happening. They’re also fair about the other side: sometimes a one-shot fix really is one, and they’ve had good results just asking the agent whether a task needs the full process.

A side benefit is that everything lives in plain files, so you can read the agent’s work in your own editor instead of in a console that keeps scrolling away.

It’s interesting how it evolved. It started as a single instruction file, but the agent forgot the instructions for the same reason it forgot the plans. So the authors split it into several files, each supplied when it’s needed, and added instructions for before, during, and after certain steps. They spent about a year refining it on real projects, mostly frameworks for online social spaces, plus some odds and ends like documentation, and kept it in its own repo so every project uses the same version.

The part I find most interesting is that it made different agents behave more consistently. They used it with Cursor, Windsurf, Copilot, Claude Code, and Codex, and under the same written process the agents started working within similar constraints. Even weaker, cheaper models did better. That matches something I’ve seen with communities. When expectations are written down and clear, a lot more participants meet them.

People will reasonably ask how this differs from the plan modes many agents now include, where the agent explores the codebase and proposes a plan for approval. That’s the same instinct, and it’s a good one. The authors point to three differences.

First, the plans are plain, searchable text files in the repo, so they survive the context window, compaction, the end of a session, and switching agents.

Second, they work as documentation. Months later, you, or your agent, even a different one, can see the thinking that went into a feature. The code shows what was done but not what was intended, and in my experience the intent is usually the harder thing to reconstruct.

Third, the process is the same across agents. The authors sometimes hand a task from Claude Code to Codex partway through, since Codex seems better at complex features and Claude Code at UI. That only works because the plan doesn’t live inside either one.

Another benefit the authors describe is that there’s much less explaining to do. Rather than describing everything up front, they let the agent write its own explanation and correct it where needed, and most of the time it has the right idea. Responding to what’s actually on the page tends to be easier than spelling everything out in the abstract.

Eventually they started recommending it to others, it helped them too, and it needed a better name than FEATURE_DEVELOPMENT_PROCESS.md. They also added a debug mode.

If you want to try it, copy it anywhere into your project, and next time you work on a feature, append “Write Step 1 of RAILSPIKE.md.” to your prompt. One caveat worth knowing: your original prompt is preserved in the generated Step 1 document, so don’t write anything you wouldn’t want ending up in your repo.

It’s fairly stable. If you want the occasional update, you can add it as a git submodule; instructions are included.

I’d be curious to hear how it works for others, especially anyone who tries it across different agents. That’s the kind of thing that makes for a good thread, as long as it stays on topic.

The workflow

Four steps. Explicit handoffs.

Use Railspike alongside your agent's plan mode to keep decisions in editable Markdown files you can revisit across sessions. After approval, plans are committed before delivery; each stage is verified and committed with its summary.

  1. 01 / ASSESS (optional)

    Assess the options

    Compare approaches, combine compatible options, and refine the recommendation when the answer is uncertain.

  2. 02 / DEFINE

    Define the outcome

    Refine the requirements, exclusions, risks, and success criteria until the scope matches your intent.

  3. 03 / PLAN

    Plan the stages

    Revise the stages, dependencies, and verification plan before committing to the work.

  4. 04 / DELIVER

    Deliver and verify

    Produce the approved code, documents, tests, or checklist on a feature branch. Verify each stage and commit it with its updated summary.

Each planning step waits for your explicit approval. After reviewing its artifact, type Approved Step N with the step number to proceed. After you approve Step 3, the agent creates a feature branch, groups the plans in docs/plans/{feature}/, and commits them with the necessary navigation repairs before implementation. If scope changes, return to planning.

When to use it

When reviewability is worth the extra step.

Use Railspike for planning, documentation, development, bug fixes, test suites, and checklists when the work has meaningful scope or decisions to resolve. A reviewed plan can be a useful handoff even before implementation begins.

The approval loop adds overhead and can be excessive for a trivial edit. It helps structure engineering judgment; the quality of the decisions still depends on you and your agent.
